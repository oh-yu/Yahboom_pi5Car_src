1. パッケージ概要

目的：差動駆動ロボット（Yahboom pi5 Car）を Gazebo 上で走らせ、 ランダムに現れる目標地点まで自律到達する方策を強化学習で獲得する、最小構成のサンプル実装。

設計思想：ROS2 の通信（cmd_vel publish / odom subscribe）を Gymnasium の Env インターフェースでラップし、 Stable-Baselines3 の PPO / SAC をそのまま適用できるようにしている点が核。 リセットは /reset_simulation、ゴール標識は毎エピソード delete→spawn で作り直す簡潔で決定的な構成とし、 将来のデジタルツイン化（Sim-to-Real）を見据えた拡張余地を持つ。

2. 全体処理フロー概要

学習は「エピソードを繰り返し、各ステップで 観測→行動→報酬 を回す」標準的な強化学習ループ。 下図は 1 エピソードの流れと、内部で走る 1 ステップ（制御周期 0.1s）の詳細を俯瞰したもの。

ロジックのポイント（一目でわかる要点）

  • 環境はROS2ノード：step() の中で cmd_vel を出し、step_dt ぶん rclpy.spin_once を回して odom を反映する。時間駆動の疑似同期。
  • 報酬は距離短縮シェイピング主体：「前ステップより目標に近づいた距離」に比例して報酬を与えるため、疎な到達ボーナスだけより学習が速い。
  • 終了は3系統：到達(成功)・境界外(失敗)＝terminated、400step超過(timeout)＝truncated。
  • reset は簡潔・決定的：/reset_simulation でワールドを初期化し、reset の非同期適用を待ってからゴールを spawn する。全エピソードで同じ手順に統一し、表示の取りこぼしを防ぐ。
  • 学習/評価/確認で環境を共有：全スクリプトが同じ YahboomGoalEnv を使うため、挙動の一貫性が担保される。

RLノード（YahboomGoalEnv）と Gazebo の間で、以下のトピック／サービスが流れる。

4. 強化学習の定式化（MDP）

状態空間 S（7次元・連続）

observation_space は Box（下記の上下限で正負対称）。

#要素意味
0dx = gx - x目標との x 偏差
1dy = gy - y目標との y 偏差
2dist目標までの直線距離
3cos(heading_err)方位誤差の cos
4sin(heading_err)方位誤差の sin
5v現在の並進速度
6ω現在の角速度

方位誤差 = atan2(dy,dx) − yaw を [-π,π] に正規化し、角度の不連続を避けるため cos/sin で表現。

行動空間 A（2次元・連続）

action_space は各成分 [-1, 1] の Box。step() でスケール変換。

linear.x = a[0] × max_linear (0.3 m/s)
angular.z = a[1] × max_angular (1.0 rad/s)

入力は clip(-1,1) 済み。行動を正規化しておくことで方策学習が安定する。

終了条件

条件種別info
dist < 0.20mterminatedis_success=True
|x|>3 or |y|>3terminatedout_of_bounds
steps ≥ 400truncatedtimeout

報酬関数 R

rt = reward_progress × (prev_dist − dist) … 距離短縮シェイピング（+30 / m）
   + reward_step (−0.01) … 生存ペナルティ（早期到達を促す）
   + reward_action × Σaᵢ² (−0.001) … 大きな行動へのペナルティ
＋ 終端時： 到達 +100 / 境界外 −50

シェイピング主体のため報酬が密になり、疎な到達ボーナスのみより収束が速い。 注：タイムアウト(truncated)時は失敗ペナルティ(−50)は加算されない（境界外のみ加算）。

4.5 前提知識：PID制御と、RLの「模範解答」

PID制御とは（前提知識）

PID制御は、目標値と現在値の誤差 e(t) から操作量 u(t) を決める、最も基本的なフィードバック制御則。 「今の誤差(P)」「誤差の累積(I)」「誤差の変化(D)」の3項を重み付けして足し合わせる。

u(t) = Kp·e(t)  +  Ki·∫e(t)dt  +  Kd·de(t)/dt
項役割直感
P（比例）現在の誤差に比例して即応目標から遠いほど強く操作
I（積分）誤差の累積を消す定常的なズレを粘り強く詰める
D（微分）誤差の変化を抑える行き過ぎ（オーバーシュート）を減衰

本パッケージの demo_reach.py は、このうち P項だけを使った簡易版（P制御）で、 「目標方向へ旋回し、正面を向いたら前進」という制御則を人手で書き下している。

なぜPIDが「学習対象の模範解答」なのか

強化学習(RL)は正解の行動ラベルを一切与えない。報酬というスカラー値だけを頼りに、 方策（observation→action の写像＝ニューラルネット）を試行錯誤で獲得する。 一方 PID/P制御は、人間が「こう動けば目標に着く」という制御則を直接埋め込んだオラクル（模範解答）である。

つまり両者は目的（目標到達）が同じで、手段が違う。 PID制御を先に理解しておくと、「RLが最終的に獲得したい振る舞いの、分かりやすい一例」が手に入る。 demo_reach.py が確実に到達できることは、 「環境（reset・報酬・到達判定・ゴール表示）が正しく機能している」ことの証明にもなり、 その上で「RLはこの模範解答に匹敵する（あるいは超える）方策を、ゲイン設計なしで自力で見つけられるか？」を問う土台になる。

PID / P制御（demo_reach）強化学習（train/evaluate）
制御則の形固定の数式 u=Kp·e+…ニューラルネット（任意の非線形関数）
調整対象Kp, Ki, Kd の少数の係数数千〜数万の重みパラメータ
誰が決める人間が手で設計・チューニング報酬を頼りに自動で獲得
与える正解制御則そのもの（模範解答）報酬スカラーのみ（正解行動は不与）
表現力線形な誤差フィードバック中心非線形・状況依存の複雑な方策も表現可
位置づけ検証用オラクル本来の学習対象
まとめ：「人間がPIDゲインを手設計する」→「RLが報酬だけを頼りに方策を自動獲得する」への置き換え、という理解が本質。 ただしRLが学習するのはPIDという構造そのものではなく、報酬を最大化するより広い関数空間の中の方策。 結果的にPID的な挙動へ収束することも、PIDでは書けない挙動（回り込み等）を獲得することもある。

  • CLI: --timesteps(5万) --algo(ppo/sac) --n-steps(1024) --learning-rate(3e-4) --seed --save-dir --log-name。
  • Env を Monitor でラップ（monitor.csv出力）。
  • PPO：MlpPolicy, batch=64, γ=0.99, gae_λ=0.95。

  • CheckpointCallback で全体の1/5ごとに中間保存。
  • Ctrl+C 中断時も {algo}_final.zip を保存。TensorBoardログ対応。

5.4 evaluate.py — 評価

  • CLI: --model(必須) --algo --episodes(10) --deterministic --seed。
  • 学習済み .zip をロードし、決定論的方策でエピソード実行。
  • 各エピソードのリターン・長さ・成功可否を出力。
  • 最後に平均リターン±標準偏差・平均長・成功率を集計表示。

  • action_space.sample() でランダム行動。
  • Gazebo通信・報酬・境界判定を目視確認する sanity check。

5.6 demo_reach.py — P制御デモ（検証用オラクル）

  • CLI: --goal-x --goal-y（目標座標） --episodes --k-ang(1.5) --k-lin(1.2) --seed。
  • reset(options={"goal":(x,y)}) で指定ゴールに固定し、学習抜きで必ず到達させる。
  • 制御則 p_control()：方位誤差を cos/sin から復元 → 角速度 ang=clip(k_ang·he,-1,1)、前進 lin=clip(k_lin·dist,0,1)·max(0,cos he)。
  • 用途：環境（reset・報酬・到達判定・ゴール表示）の end-to-end 動作確認と、RLが目指す模範解答の提示（4.5節）。
ros2 run yahboomcar_rl demo_reach --goal-x 1.5 --goal-y 0.5

5.7 goal_reach_launch.py — 同時起動

display_gazebo.launch.py をincludeし、TimerAction(period=8s) でGazebo起動後に random_agent（3エピソード）を立ち上げる動作確認用launch。学習本番は ros2 run yahboomcar_rl train の直接実行を推奨。

6. リセット & ゴール配置ロジック（簡潔・決定的）

ゴール円柱が「特定エピソードだけ表示されない／一瞬で消える」不具合を解消するため、 全エピソードで同一の決定的な手順に統一している。核心は 「/reset_simulation の非同期適用が終わってからゴールを spawn する」こと。

リセット（reset()内）

  1. 停止：cmd_vel にゼロを publish。
  2. ワールドリセット：/reset_simulation（std_srvs/Empty）を呼び完了待ち。
  3. odom復帰待ち：_odom_ready が立つまで待機。
  4. reset適用待ち：_spin_settle(0.3)。reset はランタイム spawn 済みモデルの消去を後から非同期に効かせるため、ここで確実に反映させる。
  5. ゴール再生成：_goal_spawned=False を強制し、必ず新規 spawn 経路へ。
options={"goal":(x,y)} を渡すとゴールを固定（デモ/検証用）。無指定なら _sample_goal() でランダム生成。

ゴール配置（_place_goal()）

  1. delete：既存の rl_goal を delete_entity で削除。
  2. 消滅待ち：_spin_settle(0.3) で削除の適用と同名モデル登録の解放を待つ。
  3. spawn：SDFテンプレートから赤円柱を spawn_entity。失敗時は「再delete→待機→再spawn」を最大5回リトライ。

move/再利用経路は撤去（set_entity_state は不使用）。reset との競合が無くなり、全エピソードで安定して円柱が表示される。 RViz には常に rl_goal_marker（赤球）も publish され可視化は二重化。

不具合の真因と対策（記録）

  • 症状：ep1 のみ円柱が正常表示。ep2/ep3 で「表示されない」または「一瞬出て消える」。
  • 真因：/reset_simulation はワールドを起動時状態へ戻すためランタイム spawn したゴールを消去し、しかもその処理が非同期で後から適用される。旧実装の move/再利用経路がこれと競合し、spawn 直後のゴールが reset 後処理で消されていた。
  • 対策：全エピソードを「reset 完全適用待ち → 新規 spawn」に統一（本節の手順）。ep 依存の分岐を排除し決定的化。

7. 実行手順（クイックリファレンス）

# 依存インストール
pip install "gymnasium>=0.29" "stable-baselines3[extra]>=2.3" torch numpy
sudo apt install ros-humble-gazebo-ros-pkgs ros-humble-visualization-msgs

# ビルド
cd ~/.../yahboomcar_ws
colcon build --packages-select yahboomcar_rl && source install/setup.bash

# 1) Gazebo 起動（別ターミナル）※ init/factory プラグイン付きで起動すること
ros2 launch yahboomcar_description display_gazebo.launch.py
#   （手動起動する場合は必ずプラグインを付ける）
#   gazebo --verbose -s libgazebo_ros_init.so -s libgazebo_ros_factory.so

# 2) 動作確認（全エピソードでゴール円柱が表示されるか）
ros2 run yahboomcar_rl random_agent --episodes 3

ros2 run yahboomcar_rl train --timesteps 50000 --algo ppo --save-dir ~/rl_models
tensorboard --logdir ~/rl_models

# 5) 評価
ros2 run yahboomcar_rl evaluate --model ~/rl_models/<run>/ppo_final.zip --episodes 10
