1. Package Overview

Purpose: A minimal sample that drives a differential-drive robot (Yahboom pi5 Car) in Gazebo and learns, via reinforcement learning, a policy that autonomously reaches a randomly placed goal.

Design philosophy: The core idea is to wrap ROS2 communication (cmd_vel publish / odom subscribe) in the Gymnasium Env interface so that Stable-Baselines3 PPO / SAC can be applied as-is. Reset uses /reset_simulation, and the goal marker is re-created every episode via delete→spawn, giving a simple and deterministic design with room to grow toward a future digital twin (Sim-to-Real).

2. End-to-end Processing Flow

Training is the standard RL loop: repeat episodes, and at each step cycle through observation → action → reward. The figure below gives a bird's-eye view of one episode and the detail of one internal step (control period 0.1s).

Logic at a glance (key points)

  • The env is a ROS2 node: inside step() it publishes cmd_vel, spins rclpy.spin_once for step_dt, and reflects odom. A time-driven pseudo-synchronization.
  • Reward is mainly distance-progress shaping: reward is proportional to "how much closer to the goal than the previous step", which trains faster than a sparse reach bonus alone.
  • Three termination paths: reached (success) and out-of-bounds (fail) = terminated; exceeding 400 steps (timeout) = truncated.
  • Reset is simple and deterministic: /reset_simulation initializes the world, and the goal is spawned only after the reset has been asynchronously applied. The same procedure is used for every episode to prevent missed rendering.
  • Env shared across train/eval/check: every script uses the same YahboomGoalEnv, guaranteeing consistent behavior.

4. RL Formulation (MDP)

State space S (7-D, continuous)

observation_space is a Box (symmetric lower/upper bounds below).

#ElementMeaning
0dx = gx - xx offset to goal
1dy = gy - yy offset to goal
2diststraight-line distance to goal
3cos(heading_err)cos of heading error
4sin(heading_err)sin of heading error
5vcurrent linear velocity
6ωcurrent angular velocity

heading error = atan2(dy,dx) − yaw, normalized to [-π,π] and expressed as cos/sin to avoid angular discontinuity.

Action space A (2-D, continuous)

action_space is a Box with each component in [-1, 1], scaled inside step().

linear.x = a[0] × max_linear (0.3 m/s)
angular.z = a[1] × max_angular (1.0 rad/s)

Input is already clip(-1,1)-ed. Normalizing actions stabilizes policy learning.

Termination conditions

ConditionKindinfo
dist < 0.20mterminatedis_success=True
|x|>3 or |y|>3terminatedout_of_bounds
steps ≥ 400truncatedtimeout

Reward function R

rt = reward_progress × (prev_dist − dist) ... distance-progress shaping (+30 / m)
   + reward_step (−0.01) ... survival penalty (encourages fast reaching)
   + reward_action × Σaᵢ² (−0.001) ... penalty on large actions
+ terminal: reached +100 / out-of-bounds −50

Because it is shaping-based, the reward is dense and converges faster than a sparse reach bonus alone. Note: on timeout (truncated) the fail penalty (−50) is NOT added (only out-of-bounds adds it).

4.5 Background: PID Control and the RL "Model Answer"

What PID control is (background)

PID control is the most fundamental feedback control law: it determines the control output u(t) from the error e(t) between the target and current value. It weighs and sums three terms: "present error (P)", "accumulated error (I)", and "rate of change of error (D)".

u(t) = Kp·e(t)  +  Ki·∫e(t)dt  +  Kd·de(t)/dt
TermRoleIntuition
P (proportional)immediate response proportional to current errorthe farther from goal, the stronger the action
I (integral)eliminates accumulated errorpatiently closes steady-state offset
D (derivative)suppresses rate of change of errordamps overshoot

This package's demo_reach.py is a simplified version using only the P term (P-control), hand-coding the rule "turn toward the goal, then move forward once facing it."

Why PID is the "model answer" for the learning target

Reinforcement learning (RL) provides no correct action labels at all. Relying only on a scalar reward, it acquires a policy (a mapping observation→action, i.e. a neural network) by trial and error. PID / P-control, by contrast, is an oracle (model answer) into which a human directly embeds the control law "move like this to reach the goal".

In other words, the two share the same goal (reaching the target) but differ in means. Understanding PID first gives you a clear example of the behavior RL ultimately wants to acquire. The fact that demo_reach.py can reach the goal reliably also proves that the environment (reset, reward, reach detection, goal rendering) is functioning correctly, and it lays the foundation for the question: "Can RL find a policy that matches (or exceeds) this model answer, without any gain design?"

PID / P-control (demo_reach)Reinforcement Learning (train/eval)
Form of the control lawfixed formula u=Kp·e+…neural network (arbitrary nonlinear function)
What is tuneda few coefficients Kp, Ki, Kdthousands to tens of thousands of weights
Who decidesdesigned / tuned by handacquired automatically from reward
Supervision giventhe control law itself (model answer)only scalar reward (no correct actions)
Expressivenessmostly linear error feedbackcan express nonlinear, context-dependent policies
Positioningverification oraclethe actual learning target
Summary: the essence is the shift from "a human hand-designs PID gains" to "RL automatically acquires a policy relying only on reward." However, what RL learns is not the PID structure itself but a policy in a much wider function space that maximizes reward. It may converge to PID-like behavior, or acquire behavior that PID cannot express (e.g. curving around).

6. Reset & Goal Placement Logic (simple, deterministic)

To fix the bug where the goal cylinder "does not render in certain episodes / flashes and disappears", every episode is unified to the same deterministic procedure. The key is to "spawn the goal only after the asynchronous application of /reset_simulation has finished."

Reset (inside reset())

  1. Stop: publish zero to cmd_vel.
  2. World reset: call /reset_simulation (std_srvs/Empty) and wait for completion.
  3. Wait for odom: wait until _odom_ready is set.
  4. Wait for reset applied: _spin_settle(0.3). Reset deletes runtime-spawned models asynchronously afterwards, so we make sure it takes effect here.
  5. Re-create goal: force _goal_spawned=False to always take the fresh-spawn path.
Passing options={"goal":(x,y)} fixes the goal (for demo/verification). Without it, _sample_goal() generates a random goal.

Goal placement (_place_goal())

  1. delete: remove the existing rl_goal via delete_entity.
  2. Wait for removal: _spin_settle(0.3) to let the delete apply and release the same-name model registration.
  3. spawn: spawn the red cylinder from the SDF template. On failure, retry "delete→wait→spawn" up to 5 times.

The move/reuse path is removed (set_entity_state is not used). This eliminates the race with reset, so the cylinder renders stably in every episode. rl_goal_marker (red sphere) is also always published to RViz, giving redundant visualization.

Root cause and fix (record)

  • Symptom: only ep1 rendered the cylinder correctly. In ep2/ep3 it "did not render" or "appeared briefly then vanished".
  • Root cause: /reset_simulation returns the world to its startup state, so it deletes the runtime-spawned goal, and that processing is applied asynchronously afterwards. The old move/reuse path raced with this, and the goal spawned just before was deleted by reset's post-processing.
  • Fix: unify all episodes to "wait for reset fully applied → fresh spawn" (the procedure in this section). Episode-dependent branching was removed to make it deterministic.

7. How to Run (quick reference)

# install dependencies
pip install "gymnasium>=0.29" "stable-baselines3[extra]>=2.3" torch numpy
sudo apt install ros-humble-gazebo-ros-pkgs ros-humble-visualization-msgs

# build
cd ~/.../yahboomcar_ws
colcon build --packages-select yahboomcar_rl && source install/setup.bash

# 1) Start Gazebo (separate terminal) - must load init/factory plugins
ros2 launch yahboomcar_description display_gazebo.launch.py
#   (if starting manually, always add the plugins)
#   gazebo --verbose -s libgazebo_ros_init.so -s libgazebo_ros_factory.so

# 2) Sanity check (verify the goal cylinder renders in every episode)
ros2 run yahboomcar_rl random_agent --episodes 3

# 3) Verify: reliably reach via P-control (env end-to-end check)
ros2 run yahboomcar_rl demo_reach --goal-x 1.5 --goal-y 0.5

# 4) Train
ros2 run yahboomcar_rl train --timesteps 50000 --algo ppo --save-dir ~/rl_models
tensorboard --logdir ~/rl_models

# 5) Evaluate
ros2 run yahboomcar_rl evaluate --model ~/rl_models/<run>/ppo_final.zip --episodes 10
